# PR Review Resolver

## Навіщо це потрібно саме в такому вигляді

Цей скіл існує тому, що дві попередні спроби закривати рев'ю PR власноруч
провалювались по-різному, і обидві провали задокументовані:

- **Один і той самий баг (Enter сабмітить форму передчасно) пройшов три
  раунди виправлень**, і жоден раз причину не знайшов жоден інструмент —
  тільки ручне тестування користувачки. Найважливіша знахідка звідти:
  фікси робились напряму, без делегування `debug-assistant`/`qa-agent`, і
  жоден з них не запускався навіть жодного разу за сесію. Якби кожен фікс
  послідовно передавався `debug-assistant`, той з більшою ймовірністю
  поставив би питання про browser-семантику `<form>` вже на першому раунді.
- В іншому рев'ю (interactive drag-компонент на кшталт range-слайдера)
  статичні скіли (`senior-frontend-standards`,
  `styling-expert`, `jest-rtl-senior-tests`) викликались справно, але
  зовнішнє рев'ю все одно знайшло 1 blocking + 13 non-blocking + 16
  suggestion зауважень — переважно там, де заміна одного механізму на
  "еквівалентний" (`aria-hidden`↔`inert`, per-element pointer capture↔
  глобальні `window`-слухачі, ref-мірор у хибний бік) не була перевірена
  на всіх, хто на цей механізм покладався.

Тому в цьому скілі **делегування конкретному скілу — обов'язкова перевірка
перед кожним фіксом**, а не рекомендація, яку легко пропустити під тиском
"просто виправити швидко".

## Крок 0 — Переконайся, що доступ до GitHub реально є

```bash
gh --version   # чи CLI взагалі встановлений
gh auth status # чи залогінений, і на який акаунт/хост
```

- **`gh` не знайдено** — не намагайся сліпо `brew install gh`; спершу
  перевір `command -v brew`. Якщо Homebrew теж немає — або проведи
  користувачку через інтерактивне встановлення (потребує пароля, який
  Claude не може ввести неінтерактивно), або запропонуй завантажити
  готовий бінарник `gh` з `github.com/cli/cli/releases` у `PATH` без sudo.
- **`gh` встановлений, але не залогінений** — це дія користувачки, не твоя:
  `gh auth login` вона виконує сама (fine-grained token, обмежений цим
  репозиторієм, scope `Pull requests: Read & write` + `Issues: Read &
  write`). Ніколи не проси токен у чаті.
- **Залогінений не на той акаунт / бракує прав** — скажи конкретно, який
  акаунт і яких прав бракує, а не загальне "auth не спрацював".

Переходь до Кроку 1 лише коли `gh auth status` підтверджує потрібний хост і
акаунт.

## Крок 1 — Зібрати кожен коментар з обох джерел

З'ясуй PR у фокусі (номер/URL від користувачки, або `gh pr view
--json number,url` з поточної гілки). Витягни коментарі з *обох* потоків —
рев'ювери користуються обома, і пропустити один означає пропустити частину
фідбеку:

```bash
# Inline-коментарі, прив'язані до рядка/треду в diff
gh api repos/{owner}/{repo}/pulls/{pr_number}/comments --paginate

# Загальні коментарі до розмови (не прив'язані до рядка diff)
gh api repos/{owner}/{repo}/issues/{pr_number}/comments --paginate
```

Якщо є збережений файл рев'ю (напр. `.claude/reviewer/pr-NN-review.md`) —
прочитай і його: там часто більше контексту (кроки відтворення, вже
ухвалені рішення), ніж у сирому payload з GitHub.

Для кожного коментаря запам'ятай: id, тип (`pulls/comments` з `path` +
`in_reply_to_id`, чи `issues/comments` без тредів), файл/рядок, текст
рев'ювера дослівно, чи в треді вже є відповідь (пропускай оброблені треди,
якщо користувачка явно не просить повернутись).

## Крок 2 — Критична класифікація, потім план і затвердження

**Стався до кожного зауваження критично** — перевіряй, чи воно дійсно
відповідає дійсності й доречне, перш ніж класти його в план як "погоджено":

- Відкрий файл/рядок, на який посилається коментар, і перевір твердження
  по коду, а не на віру рев'юверу.
- Якщо коментар критикує заміну одного механізму на "еквівалентний"
  (`aria-hidden`↔`inert`, event capture↔глобальні listeners, напрямок
  ref-мірора, зміна способу приховування/монтування DOM-вузла) — явно
  перевір (`grep`) увесь код, що покладався на старий механізм, а не
  просто повір, що новий варіант коректний з першого погляду. Саме такі
  "тихі" заміни давали blocking-баги, які статичні скіли пропускали.
- Якщо коментар зачіпає широкий blast radius (глобальний CSS reset,
  перейменування, підняття спільного елемента вище по дереву) — перевір
  факт впливу пошуком інших використань, а не масштаб зміни "на око".
  Обидва висновки можливі: широка зміна іноді виявляється безпечною
  (вузький фактичний blast radius), а іноді ні — важливо саме перевірити,
  не вгадати.
- Якщо після перевірки лишається сумнів чи незгода — не заганяй коментар у
  "погоджено" лише щоб спростити план. Познач його як "потребує обговорення
  з рев'ювером" і готуй текст відповіді, а не фікс.

Структуруй усі коментарі по **блоках виправлення** (логічно пов'язані
пункти йдуть в один блок — один компонент, одна причина, одна ділянка
коду). Для кожного блоку зафіксуй: список коментарів усередині, файли, які
торкнуться, і який скіл тулкіта буде викликаний (див. Крок 3) — це вже
частина плану, не рішення "по ходу".

Створи й затверди цей план **через скіл `feature-delivery-workflow`** —
персистентний файл `.claude/planning/pr-<NN>-review.md`, один блок = один
пункт плану = один коміт. Не починай виправляти жоден блок, поки план не
показаний користувачці і не підтверджений.

## Крок 3 — Перед КОЖНИМ блоком: назви скіл, якому делегуєш, і виклич його

Це найважливіший урок з попередньої сесії, і тому — жорстке правило, а не
пропозиція: **перш ніж торкатись коду блоку, явно скажи, якому скілу
делегується виправлення, і викликай саме його** — не пиши фікс напряму від
себе, навіть якщо здається очевидним і швидким.

| Тип зауваження в блоці | Делегувати |
|---|---|
| Баг, незрозуміла поведінка, регресія в логіці, browser-семантика (форми, події, фокус) | `debug-assistant` |
| Типізація, архітектура, структура компонента/хука, Redux Toolkit | `senior-frontend-standards` |
| SCSS, токени, breakpoint, focus-стилі, magic values | `styling-expert` |
| Відсутнє/недостатнє тестове покриття, симетричні/дзеркальні кейси без тесту | `jest-rtl-senior-tests` |
| Потрібне повторне структуроване рев'ю самого фіксу перед тим, як показати результат | `code-reviewer` |

Якщо блок охоплює кілька типів (наприклад, баг + бракуючий тест на нього) —
делегуй кожній частині свій скіл послідовно, а не одному навмання. Якщо
жоден з наведених скілів явно не підходить (наприклад, суто текстова
правка) — так і скажи прямо, чому цей блок робиться напряму, а не мовчки
пропускай крок делегування.

## Крок 4 — Виконати блок і видати список фіксів

Після того, як делегований скіл відпрацював (фікс застосовано, статичні
перевірки — `tsc`/lint/тести — пройшли), зведи для користувачки короткий
список змін у цьому блоці: файл → що змінилося → яке зауваження це
закриває. Це те, що вона перевірятиме в Кроці 5 — не переказуй diff
рядок за рядком, дай саме мапу "коментар → фікс".

## Крок 5 — Користувачка перевіряє код сама

Після списку фіксів — зупинись і чекай. Це її самостійна перевірка коду,
не формальність: не пропонуй одразу коміт, не квапся до наступного блоку.

## Крок 6 — Формування коміту, потім реальний коміт після дозволу

Коли користувачка підтвердила зміни блоку — сформуй commit-повідомлення і,
якщо потрібно для опису PR пізніше, ключові пункти — форматом зі скіла
`git-workflow` (Conventional Commits + gitmoji, Крок 4 того скіла). Покажи
точний текст і diff, і чекай окремого явного "так" саме на коміт **цього
блоку** — дозвіл з попереднього блоку сюди не переноситься, навіть у межах
тієї самої сесії.

Лише після цього "так" виконай сам `git commit` з цим текстом. (`git
push`/відкриття PR цим скілом не виконуються — це окремі дії з окремим
дозволом, як і в решті тулкіта.) Онови `.claude/planning/pr-<NN>-review.md`
(галочка + хеш коміту) і переходь до наступного блоку — повертайся до Кроку
3 для нього.

## Крок 7 — Коли всі блоки виправлені: реакції та відповіді

Коли кожен блок пройшов Кроки 3–6, зведи один консолідований список по
кожному вихідному коментарю з Кроку 1, у порядку рев'ювера:

```
[#<comment-id>] <файл:рядок або "загальний коментар">
Рев'ювер (мовою оригіналу): "<коментар, дослівно або стисло>"
Суть українською: <що просить рев'ювер і чому це важливо>
План: 👍 REACT — <який фікс приземлився і як перевірений, українською>
   -- або, якщо коментар не потребував зміни коду --
План: 👍 REACT (фікс не потрібен) — <чому, українською>
   -- або, якщо є незгода чи часткова згода (див. Крок 2) --
План: REPLY (англійською) — <точний текст, дослівно, не переказ>
```

**Мовне правило:** суть і пояснення в цьому плані — завжди українською.
Текст `REPLY`, що реально піде на GitHub, — англійською (мова рев'ю
проєкту), дослівно так, як буде опубліковано — не переказуй його
українською в самому плані.

Ніколи не став 👍 на коментар, що вимагав зміни коду, поки фікс не
застосований і не перевірений (це вже гарантовано ходом Кроків 3–6, але
перевір ще раз тут, перед постингом). Дочекайся окремого явного дозволу
користувачки саме на постинг — окремо від дозволів на коміти з Кроку 6.

Постуй лише після дозволу, через правильний ендпоінт для кожного типу:

```bash
# Відповідь у тред inline review-коментаря
gh api repos/{owner}/{repo}/pulls/{pr_number}/comments \
  -f body="<схвалений текст, англійською>" -F in_reply_to={comment_id}

# Відповідь на загальний issue-коментар (без тредів)
gh api repos/{owner}/{repo}/issues/{pr_number}/comments -f body="<схвалений текст, англійською>"

# Реакція 👍 на inline review-коментар
gh api repos/{owner}/{repo}/pulls/comments/{comment_id}/reactions -f content="+1"

# Реакція 👍 на загальний issue-коментар
gh api repos/{owner}/{repo}/issues/comments/{comment_id}/reactions -f content="+1"
```

Після постингу підтверди користувачці коротким списком, що саме пішло
(comment id → що сталося), українською.

## Крок 8 — Повна регресійна перевірка через `qa-agent`

Після постингу — прожени **окремий, самостійний виклик** `qa-agent` по всій
гілці цілком, не по одному блоку за раз: власні точкові перевірки в
браузерному MCP не замінюють його чек-лист (крос-браузерність, тач, edge
cases, збережений звіт) — це те саме правило, що й у
`feature-delivery-workflow`.

Додатково, специфічно для цього скіла (винесено з реального провалу):

- Якщо будь-який блок торкався `<form>`/`onSubmit`/`type="submit"` —
  тест-план `qa-agent` повинен явно включати: "Enter у кожному полі форми
  (текстовому, radio, combobox) не сабмітить форму передчасно, лише клік по
  кнопці". Не покладайся на власноручну перевірку в браузері замість цього.
- **Синтетичні (non-trusted) DOM-події не доводять нативну поведінку
  браузера.** `dispatchEvent(new KeyboardEvent(...))` не відтворює
  implicit-submit форми чи навігацію `<a>` — для такої верифікації потрібен
  справжній keypress через реальний браузерний інструмент, а не JS
  dispatchEvent.

Якщо `qa-agent` знаходить нову регресію — це новий блок: повернись до Кроку
2 для нього (класифікація й делегування), не виправляй нашвидкуруч в обхід
цього ж циклу.

## Крок 9 — Ретроспектива: чого не вистачило скілам

Коли регресія з Кроку 8 чиста (або відомі залишки свідомо прийняті
користувачкою) — проаналізуй сесію: де саме зауваження рев'ювера вказали на
щось, чого жоден зі скілів тулкіта не зловив би сам (статичним аналізом чи
власним чек-листом), і чому саме. Не обмежуйся загальним "будь уважнішою" —
формулюй як конкретну інструкцію, яку можна вставити в SKILL.md.

Збережи цей аналіз у файл **у проєкті, над яким велась робота** (не в цьому
репозиторії плагіна): `./claude/upgrade-skills/<коротка-назва>.md`. Рішення,
чи і коли вносити ці правки в самі скіли плагіна — за користувачкою; цей
крок лише фіксує знахідки, не редагує SKILL.md автоматично.

## Guardrails

- Ніколи не пости відповідь чи реакцію, поки користувачка не побачила той
  самий текст на Кроці 7 і не сказала продовжувати.
- Ніколи не став 👍 на коментар кошика "потрібна зміна коду", поки фікс
  реально не застосований і не перевірений.
- Ніколи не виконуй `git commit` без окремого явного "так" саме для
  поточного блоку — дозвіл із попереднього блоку не переноситься.
- Ніколи не виконуй `git push`, `gh pr create` чи `gh pr merge` цим
  скілом — це окремі дії з окремим дозволом поза межами цього циклу.
- Ніколи не пропускай Крок 3 (явне делегування) "бо фікс очевидний" — саме
  ця економія коштувала три раунди виправлень одного бага в минулому.
- Якщо доступ до GitHub ламається посеред роботи (токен відкликано,
  rate-limit, не той репозиторій) — зупинись і перевір Крок 0 наново, а не
  вгадуй чи повторюй наосліп.
- Якщо в треді вже є відповідь з цього акаунта — вважай оброблено, не
  дублюй, якщо користувачка явно не просить повернутись до теми.
