# Code Reviewer

Проводить структуроване рев'ю diff'а або набору файлів. Це скіл ДЛЯ Claude —
інструкції нижче виконуються, а не переказуються користувачу.

## Коли викликається

1. **Явно** — людина просить ревью коду напряму.
2. **Напівавтоматично з `git-workflow`** — перед тим, як `git-workflow`
   згенерує опис Pull Request (Крок 5 у `git-workflow`), він застосовує
   критерії цього скіла до diff'а. Це не hard-блокування на рівні
   інструменту (немає окремого технічного PreToolUse hook для цього
   кроку) — це логічний крок усередині самого `git-workflow`, який
   виконується щоразу перед генерацією PR-опису.

### Цей скіл сам по собі не закриває запит на тестування

Перевір формулювання запиту **до того, як почнеш рев'ю**. Якщо в ньому є
"протестуй", "перевір на баги", "знайди баги", "чи все працює", "чи готово
до релізу", "задій усі потрібні скіли" або будь-яка вимога живої перевірки —
самого рев'ю коду **недостатньо**: обов'язково застосуй ще й `qa-agent`.

Статичний аналіз і живий прогін знаходять різні класи дефектів. Баг, який
видно тільки в рантаймі (обірваний жест, розсинхрон стану, розбіжність між
рушіями), рев'ю коду не побачить у принципі.

**Найчастіша помилка:** браузерні інструменти доступні напряму, тому виникає
спокуса "просто зайти й подивитись" замість того, щоб застосувати `qa-agent`.
Так втрачається весь його чек-лист — крос-браузерність, тач, edge cases,
негативні сценарії, збереження звіту. Якщо потрібна жива перевірка —
застосовуй скіл, а не тільки інструменти.

Якщо браузер недоступний — так і скажи, і познач живу перевірку як
непроведену в секції "Межі охоплення", а не мовчи.

## Три правила, які визначають якість рев'ю

Ці правила важливіші за будь-який чек-лист нижче. Порушення будь-якого з них
робить звіт гіршим, навіть якщо всі знахідки формально правильні.

### Правило 1: кожна знахідка має наслідок

Для **кожної** позиції у звіті сформулюй, що конкретно зламається:
- **user-visible** — що побачить чи не зможе зробити користувач;
- або **maintenance** — що конкретно стане дорожчим/крихкішим у підтримці.

Формулювання "порушує правило X" наслідком **не є**. Це опис симптому, а не
його ціни.

> **Немає наслідку → це не знахідка.** Виноси таке в окрему секцію
> "Гіпотези" з поміткою, що саме треба відтворити, щоб воно стало знахідкою,
> або не пиши взагалі. Не підвищуй серйозність через те, що правило
> "важливе на вигляд".

Приклад різниці:
- ❌ "Бізнес-логіка в компоненті замість хука — порушення розділення
  відповідальності." — правило, не наслідок.
- ✅ "Обробник продубльований у `ProductCard` і `ProductInformation`; копія
  втратила рядок `const router = useRouter()` — це вже дало помилку збірки."
  — доведений наслідок.

### Правило 2: одна знахідка = одна причина

Заборонено об'єднувати позиції за ознакою "порушено одне й те саме правило".
Якщо чотири файли порушують правило з різних причин і потребують різних
виправлень — це чотири знахідки з різними рівнями серйозності, а не одна.

Ознака порушення цього правила: всередині однієї позиції з'являється список
файлів, для яких фікси описані по-різному.

### Правило 3: серйозність визначається наслідком, а не правилом

Не "це `any`, отже критично", а "через це падає збірка / це недоступно з
клавіатури / це косметика". Одне й те саме правило може дати різну
серйозність у різних місцях.

## Рівні серйозності

Єдина шкала для всього тулкіта — та сама, що в `qa-agent`. Назва рівня
описує **наслідок**, а не відчуття важливості: рівень не можна обрати "на
око", його диктує те, що саме ламається.

| Рівень | Наслідок | Блокує PR |
|---|---|---|
| 🔴 **Blocker** | Не збирається / не деплоїться; crash; втрата даних | так |
| 🟠 **Error** | Падає в рантаймі або працює неправильно на шляху користувача | так |
| 🟡 **Inaccessible** | Недоступно з клавіатури, скрінрідера, певного рушія чи на тачі | так |
| 🔵 **Friction** | Працює правильно, але користувачу гірше/незрозуміло | ні |
| ⚪ **Hygiene** | Користувач не бачить; впливає на підтримуваність | ні |

**Blocker, Error та Inaccessible блокують PR.** `Inaccessible` блокує нарівні
з рештою свідомо: недоступний з клавіатури елемент — це не "покращення
доступності понад мінімум", а непрацюючий для частини користувачів
функціонал. Не знижуй рівень такій знахідці через те, що фікс дрібний.

Секрети (API-ключі, токени, паролі) — **завжди Blocker**, незалежно від того,
чи щось ламається: негайно познач і замаскуй значення в самому звіті.

### Що куди потрапляє

**🔴 Blocker — не збирається**
- Помилки типізації, які ловить `tsc --noEmit` (неоголошена змінна,
  відсутній імпорт типу, невідповідність сигнатур)
- Синтаксично/типово некоректний код, що зупиняє `next build`
- Секрети в коді

**🟠 Error — падає або працює неправильно в рантаймі**
- Необроблений виняток на шляху користувача (виклик API браузера без
  `try/catch` там, де він може кинути — `localStorage` у private mode тощо)
- Дані із зовнішнього джерела (localStorage, URL, відповідь API), прийняті
  без валідації форми і передані далі в стор/UI
- Посилання чи редірект на неіснуючий роут
- Форма чи контрол, які візуально працюють, але не роблять нічого
- Race condition, витік підписки/слухача, який реально доживає до наступного
  рендера

**🟡 Inaccessible — недоступно частині користувачів**
- `<div onClick>` без `tabIndex` і `onKeyDown` замість `<button>`
- Фокусований елемент без обробника (тупиковий tab-stop)
- Інтерактивний елемент без `:focus-visible` при глобальному `outline: none`
- Суперечливі ARIA-сигнали на одному елементі (наприклад `role="img"` +
  `aria-hidden` + `tabIndex={-1}` на `<button>`)
- Конфлікт двох моделей навігації одночасно (власний `tabIndex` на елементах
  при вже реалізованому roving через `aria-activedescendant`)
- Кнопка-іконка без доступної назви; декоративна іконка без `aria-hidden`
- Функціонально важлива дія, доступна лише через `:hover` (недосяжна на тачі)

**🔵 Friction — працює, але користувачу гірше**
- Відсутній стан Empty/Error там, де користувач може в нього потрапити
- Зайвий раунд ререндера з видимим мерехтінням контенту
- Відсутність `aria-live` для динамічного повідомлення (контент доступний,
  але зміна не озвучується)
- Незрозумілий чи надлишковий крок у сценарії

**⚪ Hygiene — користувач не бачить**
- `any`, `enum`, `interface`/`type` не за призначенням — **за замовчуванням
  сюди**, і піднімається до Blocker, тільки якщо реально ламає збірку
- Magic values замість токенів теми
- Дублювання **правила** (не просто схожий текст, а однакова логіка
  прийняття рішення) у двох і більше місцях без доведеного наслідку (DRY)
- Багатопольовий запис стану (кілька полів об'єкта одночасно) з умовною
  логікою прямо в компоненті/обробнику замість reducer'а/сервісу —
  порушення Information Expert (стан має оновлювати той, хто ним володіє)
- Компонент/хук отримує ширший об'єкт/пропс, ніж реально використовує,
  замість вузького типізованого інтерфейсу (ISP)
- Перевірка типу помилки за текстом рядка (`error.message === '...'`)
  замість стабільного коду/дискримінанта — крихко до зміни формулювання
- Модуль з процес-широким станом (кеш, черга, лічильник), що містить
  тестовий бекдор на кшталт `__resetForTests`, замість інкапсуляції стану
  в класі (Pure Fabrication)
- Нова абстракція (клас, generic, інтерфейс) без другого реального
  споживача/варіанту, що її виправдовує — передчасна генералізація
  (YAGNI); не плутати з відсутньою абстракцією, якої бракує (це вище, DRY)
- Опечатки, неймінг, мертвий код
- Відсутні тести (див. окреме правило нижче)

## Обов'язкові перевірки понад diff

### CI-гейт — перевіряти першим

Перед розбором самого коду перевір, чи існує автоматичний захист:
- `.github/workflows/**` (або інший CI-конфіг) з кроками `typecheck` → `lint`
  → `test` → `build`;
- скрипт `typecheck` (`tsc --noEmit`) у `package.json`;
- pre-commit хуки (`.husky/`, `lint-staged`).

**Якщо гейта немає, а в коді знайдено хоч один Blocker** — це окрема знахідка
рівня "процес", і в звіті вона йде **вище** всіх інших. Формулювання
наслідку: зламана збірка змогла дожити до ручного рев'ю саме тому, що її
ніхто не перевіряв автоматично. Пропонуй додати гейт як перший пункт робіт,
до виправлення самих багів.

Не приписуй відсутності юніт-тестів провину за помилку рівня Blocker: помилку
типізації ловить `tsc` миттєво й безкоштовно, тест на неї не потрібен.

### Diff, що торкається `<form onSubmit>`/`type="submit"` — окрема перевірка

Якщо diff додає, змінює `<form onSubmit>` чи `type="submit"`, або підіймає
`<form>` вище по дереву компонентів — постав явне питання: *"чи усвідомлено
і покрито тестом, що Enter у кожному текстовому/radio/combobox полі
всередині цієї форми тепер теж тригерить сабміт?"* Це browser-поведінка, не
видна з самого коду напряму (немає typo, немає очевидного "магічного
значення"), тому легко пропустити при читанні diff'а — саме тому це окрема
явна перевірка, а не частина загального "форми: валідація + сабмі" пункту.

Дублювання guard-логіки (той самий патерн `onKeyDown` → `preventDefault`,
скопійований у двох і більше дочірніх компонентах форми) — це і сигнал
DRY-порушення (підняти в один спільний обробник на рівні форми), і ознака,
що питання про Enter-семантику виникло вже постфактум, а не до фікса.

### Diff обгортає сторонній dismiss/focus-менеджер — окрема перевірка

Якщо diff додає чи змінює обгортку над стороннім dismiss/focus-менеджером
(floating-ui, react-aria, Radix) — явно перелічи **всі** шляхи
закриття/скидання стану (Escape, outside-click, Tab-away, програмний виклик)
і перевір, що кожен з них веде через ту саму функцію скидання стану, а не
лише той шлях, що на видноті в diff'і. Баг такого класу — коли компонент
отримує сирий сеттер (`setIsOpen`) поруч із власним `onClose`-обробником, і
бібліотечний dismiss (наприклад `useDismiss` в floating-ui на outside-click)
обходить `onClose`, лишаючи застарілий стан при повторному відкритті —
проявляється лише на послідовності з кількох кроків (відкрити → взаємодіяти
→ закрити НЕ очевидним шляхом → відкрити знову). Читання diff'а рядок-за-
рядком не змушує мисленно прогнати весь цикл станів через усі шляхи виходу,
тому це окрема явна перевірка, а не частина загального огляду компонента.

### Тести — за цінністю, а не за фактом відсутності

Відсутність тесту — знахідка тільки якщо сформульовано, що саме зламається
непомітно. Пріоритет:
- **Висока цінність** — вузькі перевикористовувані хуки та утиліти з власним
  інваріантом (focus trap, keyboard navigation, click-outside, scroll lock),
  чиста бізнес-логіка, редьюсери, селектори, middleware.
- **Низька цінність / не вимагати** — `renderHook`-тести на хуки-обгортки з
  одним споживачем і широким return; тести самого факту рендера.

Деталі — у скілі `jest-rtl-senior-tests`.

## Межі охоплення — декларувати обов'язково

У кінці звіту завжди окремою секцією перелічи, що **не** перевірялось. Це
захищає від того, щоб рев'ю виглядало ширшим, ніж було насправді.

Мінімальний перелік, який треба або підтвердити, або чесно назвати
пропущеним:
- **Браузери** — у яких рушіях реально проганявся живий сценарій (Chromium /
  Gecko / WebKit). Якщо не проганявся в жодному — так і напиши.
- **В'юпорти** — desktop / mobile; чи перевірялась тач-взаємодія.
- **Продуктивність і бандл** — чи вимірювались.
- **Локалізація** — чи був суцільний аудит рядків і ARIA-міток.
- **Покриття тестами** — чи запускався `--coverage`, чи оцінювалось лише за
  наявністю файлів.

Якщо живого прогону в браузері не було взагалі — не вживай формулювань
"перевірено в браузері" / "живе QA". Для живої перевірки є скіл `qa-agent`;
за потреби прямо запропонуй його запустити.

## Перевірка чужих знахідок

Якщо частина знахідок надійшла від суб-агентів, іншого рев'ю або
статичного аналізатора — **не переноси їх у звіт на віру**. Відкрий файл і
підтверди кожен Blocker/Error/Inaccessible по коду. Хибні спрацювання
трапляються регулярно
(правило застосоване без урахування контексту), і потрапивши у звіт,
вони знецінюють решту.

Якщо знахідку не підтверджено — прибери її і скажи про це прямо, а не
залишай "про всяк випадок".

Те саме стосується і власних тверджень про поведінку сторонньої бібліотеки
("ця бібліотека за замовчуванням робить X") — перевіряй по
`node_modules/<pkg>/**/*.d.ts` чи офіційній документації встановленої версії,
перш ніж вносити це у звіт як факт, а не покладайся на загальне уявлення
про API (детальніше — `debug-assistant`).

## 🟢 Passed Checks

Обери релевантне конкретному diff'у (не вигадуй пункти, які не стосуються
цих файлів):

- Colocation файлів (`Component.tsx` + типи + `Component.module.scss` поруч)
- `No any found` / `No enum found`
- Типізовані Redux-хуки (`useAppDispatch`/`useAppSelector`)
- Складні селектори через `createSelector`
- Jest-тести додані і покривають новий кейс
- `:focus-visible` та коректний `tabindex` там, де є клавіатурна навігація
- LF-кінці рядків (якщо це видно з diff'а)

## Формат звіту

```markdown
### 🔍 Code Review Report

#### ⚙️ Процес
- [тільки якщо немає CI-гейта, а знайдено Blocker]

#### 🔴 Blocker — не збирається
- `File.tsx:42`: [що знайдено]
  **Наслідок:** [що конкретно ламається]
  **Фікс:** [конкретна заміна]

#### 🟠 Error — падає в рантаймі
#### 🟡 Inaccessible — недоступно частині користувачів
#### 🔵 Friction — деградація UX
#### ⚪ Hygiene — підтримуваність

#### 🤔 Гіпотези (потребують підтвердження)
- [підозріле без сформульованого наслідку + що треба відтворити]

#### 🟢 Passed Checks
- [x] [Пройдена перевірка]

#### 📋 Межі охоплення
- Не перевірялось: [браузери / в'юпорти / перф / локалізація / coverage]
```

Порожні секції рівнів пропускай (на відміну від "Межі охоплення" — вона
обов'язкова завжди). Файлові шляхи та назви змінних пиши як у коді, решту
тексту — мовою, якою людина веде розмову.

---

## Правило зупинки при блокерах

Якщо є хоча б одна позиція рівня **Blocker, Error або Inaccessible** — не
продовжуй одразу до опису PR. Спочатку виведи звіт повністю, потім запитай:

> "У коді є N блокувальних зауважень (Blocker/Error/Inaccessible). Виправимо їх перед створенням PR?"

де N — сумарна кількість позицій цих трьох рівнів. Дочекайся відповіді:

- Погоджується виправити — допоможи виправити, потім прожени перевірку
  повторно перед тим, як `git-workflow` продовжить.
- Явно каже продовжити без виправлень — поважай рішення, передай керування
  назад `git-workflow`; не наполягай повторно в цій же розмові.

Якщо блокерів немає — покажи звіт і без додаткових питань дозволь
`git-workflow` продовжити.

## Межі скіла

- Скіл лише аналізує та звітує — сам ніколи не переписує файли без прямого
  прохання людини виправити конкретну знахідку.
- Скіл не виконує `git`-команд. Читання конфігів для перевірки CI-гейта
  (`package.json`, `.github/workflows/`) дозволене — це частина рев'ю.
  Запуск ESLint/Jest — сфера Auto Mode hook'а
  (`hooks/scripts/auto-lint-test.py`), а не цього скіла.
- Не позначай як блокер те, що є справою стилю чи смаку — рівні Blocker,
  Error та Inaccessible зарезервовані за доведеним наслідком.
- Не роздувай звіт кількістю позицій. Десять знахідок із наслідками кращі за
  сорок, з яких тридцять — переказ чек-листа.
