# Jest & React Testing Library — Senior Test Suite Generator

Скіл для генерації надійних, підтримуваних та поведінково-орієнтованих тестів для стеку
React / Next.js / Redux Toolkit / TypeScript. Мова відповіді користувачу — українська
(якщо користувач явно не попросив іншою).

## Перед тим як писати тест

1. Визнач **тип цілі**: презентаційний компонент / компонент із формою / компонент зі
   списком / компонент з async-станами (loading/success/error) / кастомний хук / Redux
   slice / Redux selector / thunk.
2. Відкрий відповідний референс-файл (див. "Де шукати шаблони" нижче) — не вигадуй
   структуру заново, використовуй перевірені паттерни та адаптуй їх під конкретний код.
2.1. Перевір, чи в корені репозиторію є проєктний testing guide (`docs/testing*.md`,
   `TESTING.md`, `CONTRIBUTING.md`) — і дотримуйся його понад загальні дефолти цього
   скіла, якщо він суперечить (наприклад, забороняє асерти по class-name там, де
   немає очевидного поведінкового атрибута — тоді шукай ARIA-атрибут, який і є
   поведінковим контрактом цього стану: `aria-activedescendant` для активного
   пункта, `aria-selected` для вибраного, а не падай назад на `toHaveClass`).
3. Якщо користувач надав сам компонент/хук/слайс — прочитай його уважно: пропси, типи,
   селектори, side-effects, зовнішні залежності (next/navigation, fetch, Redux hooks).
   Якщо коду немає в контексті — попроси його показати, не вигадуй API.
4. Якщо в наданому коді є натяки на API-ключі, токени чи паролі — одразу попередь
   користувача і замаскуй їх у виводі.

## Базові принципи (незмінні для будь-якого тесту)

- **Тестуємо поведінку, не деталі реалізації.** Шукаємо елементи так, як їх шукав би
  користувач: `getByRole` / `findByRole` → `getByLabelText` → `getByPlaceholderText` →
  `getByText`. `data-testid` — лише крайній випадок, коли немає доступного семантичного
  способу знайти елемент (і це варто прокоментувати в коді чому).
- **Ніколи не query по class-name чи тегу** (`container.querySelector('.foo')`) — це
  прив'язка до реалізації, а не до контракту компонента.
- **AAA-структура**: Arrange → Act → Assert, з порожнім рядком між блоками для читабельності.
- **Взаємодія користувача — тільки через `@testing-library/user-event`**, ніколи через
  `fireEvent` (окрім вузьких випадків, які user-event дійсно не покриває, напр.
  `fireEvent.scroll`, `pointercancel` як подія від ОС/браузера, а не від користувача).
  **Перш ніж класти виняток у код — перевір це емпірично** окремим прогоном, а не
  вір своїй пам'яті про можливості `userEvent`: `userEvent.pointer()` (з версії 14)
  покриває реальний рух вказівника й навіть drag-жести через масив кроків
  `{keys, target, coords}` — не єдиний `fireEvent`-кандидат, яким здається на перший
  погляд.
- **Асинхронність** — тільки `findBy*` або `waitFor`. Жодних `setTimeout`/штучних sleep.
- **Назви тестів описують поведінку та результат**, не механіку, і пишуться
  англійською (див. правило вище):
  - ДОБРЕ: `it('shows an error message when the profile-loading request fails')`
  - ПОГАНО: `it('works correctly')` / `it('тест 1')` / `it('показує помилку')`
- **Групування**: `describe('<Назва> Component', ...)`, `describe('use<Назва> Hook', ...)`,
  `describe('<назва>Slice', ...)`, `describe('select<Назва>', ...)`.
- **Мова всього тестового коду — завжди англійська**, незалежно від мови спілкування
  з користувачем у чаті. Це стосується `describe`, `it`/`test` описів, коментарів
  всередині тестового файлу, назв змінних і повідомлень у fixtures:
  - `describe('UserCard Component', ...)`
  - `it('shows an error message when the API request to load the profile fails', ...)`
  - ПОГАНО: `it('показує помилку, якщо запит на завантаження профілю впав', ...)`
  Пояснення поза кодом (перед/після блоку коду в чаті) залишається українською —
  англійською пишеться лише сам вміст `.test.ts`/`.test.tsx` файлу.

## Надійність тестів: типові пастки, які роблять тест зеленим, але марним

### Спосіб самої верифікації може вносити похибку — перевіряй його теж, коли результат несподіваний

"Перевір емпірично, не вір на слово" — необхідна, але недостатня умова: сам
спосіб емпіричної перевірки (позиція тимчасового тесту у файлі, ізольований
запуск замість повного) може вносити систематичну похибку, яка виглядає як
переконливий, відтворюваний результат.
- **Тимчасовий верифікаційний тест ніколи не додавай у кінець файлу** — встав
  його на місце, де реально житиме фінальний тест (або хоча б одразу після
  найближчого спорідненого), особливо якщо модуль під тестом має спільний/
  модульний стан (реєстри, синглтони, кеші) без явного скидання між тестами:
  тест у кінці файлу успадковує "протікання" стану з усіх попередніх тестів і
  може дати інший результат, ніж на своєму реальному місці.
- **Результат ізольованого запуску (`jest -t "..."`) не автоматично довіряй**
  без крос-перевірки повним прогоном файлу в реальному порядку виконання —
  особливо для хуків/утиліт із модульним станом.

### Тест на фікс бага мусить падати на нефікснутому коді

Якщо тест написаний, щоб зафіксувати виправлення — перевір, що він **червоний**,
коли фікс подумки чи тимчасово відкотити (або хоча б явно назви, який рядок
фіксу він проганяє). Тест, що зелений і до, і після фіксу, не охороняє нічого.

### Мутаційна самоперевірка — для кожної describe-групи окремо, не вибірково

Для **кожної** окремої `describe`-групи, що претендує на перевірку конкретної
поведінки (а не просто факту рендеру) — тимчасово злам саме ту частину коду,
яку ця група нібито захищає (обнули залежність, поверни стару версію рядка), і
підтверди, що хоча б один тест з групи падає. Якщо жоден не падає — тести
перевіряють не те, що заявлено в описі, і потребують переробки. Зробити цю
перевірку для однієї "головної" групи в файлі і пропустити сусідні, написані в
тому самому стилі, — та сама помилка, яку ця перевірка мала запобігти.

### Дзеркальну/межову навігацію тестувати з меж, не з середини

Для `ArrowUp`/`ArrowDown`, prev/next, min/max-clamp — тестуй з **граничних**
позицій: перший пункт, останній пункт, і "нічого не вибрано / індекс 0"
(bootstrap). Асиметрія живе на краях: `Math.min(len-1, i+1)` і
`Math.max(0, i-1)` при `i = 0` поводяться по-різному, а з середини списку обидва
напрямки виглядають симетрично й баг не видно.

### Один тест мусить проганяти тезу самої зміни, end-to-end, включно з повторним циклом

Коли тести покривають зміну поведінки — серед них має бути тест, що проганяє
**тезу зі summary коміта/PR** цілком, а не лише її окремі частини нарізно
(наприклад, теза "одна підсвітка за раз" — тест на перехід
`open → keyboard highlight → mouse → gone`, а не окремо "клавіатура підсвічує"
і окремо "миша скидає"). Плюс покривай повний цикл повторного входу
(`дія → закрити → відкрити знову`), не лише перший прохід — стан, скинутий
неправильно при закритті, часто не видно, поки не відкрити компонент вдруге.

### Рядок у хелпері "щоб не флейкало" може ховати контракт компонента

Якщо в тест-хелпер додається рядок заради стабільності (`.focus()`, зайвий
`await`, `waitFor`) — перевір, чи він не маскує реальний контракт, який
компонент **має** виконувати сам. Якщо компонент зобов'язаний зробити X
(перевести фокус, підвантажити дані) — **асертуй X** у хелпері
(`await waitFor(() => expect(list).toHaveFocus())`), а не форсуй його
(`list.focus()`) — інакше жоден тест не перевіряє, що компонент справді це
робить.

### `expect.anything()` для "зайвих" аргументів колбека — пастка

Коли `toHaveBeenCalledWith` падає через те, що реальний виклик має більше
аргументів, ніж очікувалось (типово — колбек від сторонньої бібліотеки,
наприклад `onOpenChange(open, event, reason)` у floating-ui) — **не "латай"**
дописуванням `expect.anything()` у зайві слоти. `expect.anything()` **не
збігається з `undefined`**, тож дописування його в слоти закріплює тест на
тому, що ці слоти справді заповнені — часто це plumbing сторонньої бібліотеки,
який тесту байдужий, і тест зламається на іншому валідному виклику з
меншою кількістю аргументів. Перевіряй лише ті аргументи, які цей тест реально
контролює: `expect(fn.mock.calls[0][0]).toBe(...)`, або
`toHaveBeenCalledWith(x, expect.any(Type))` тільки якщо наявність і тип того
аргументу — справді частина контракту, який тестуєш. "Тест знову зелений" не
означає "тест перевіряє те, що треба".

### Асерт на умовну CSS/DOM-властивість не прив'язуй мовчки до дефолтного конфіга

Коли асертиш CSS/DOM-властивість, яку компонент пише **умовно** залежно від
значення конфіга (placement, `dir`, variant, size), якого сам тест **не
задає** — асерт мовчки прив'язаний до дефолта цього конфіга (наприклад,
`FloatingArrow` пише inline `left` лише для `top`/`bottom`-placement; для
`left`/`right` він пише `top`, а `left` лишає `''` — тест, що читає лише
`arrow.style.left` без явного `placement`, працює тільки завдяки дефолтному
`bottom`). Або встанови конфіг явно в рендері, або зроби асерт агностичним до
нього (`Number.parseFloat(left || top)` замість `left`). Мутаційна
самоперевірка це не ловить — вона підтверджує лише, що асерт реагує на злам
коду, а не що він стійкий до майбутньої зміни харнеса/дефолту.

### Тип тестового харнеса — застосовуй те саме ISP, що й до продакшн-коду

Коли тестовий харнес приймає `Partial<ComponentProps>` (чи подібне) і водночас
сам жорстко визначає один чи кілька пропсів компонента (найчастіше `children`
через власний `render`-контент) — явно `Omit` ці пропси з типу харнеса
(`Partial<Omit<ComponentProps, 'children'>>`). Інакше публічний тип харнеса
обіцяє контроль, якого він не дає, і хтось згодом передасть проп, який мовчки
зникне. Це те саме ISP-правило, що вже застосовується до звичайних
компонентів/хуків (`code-reviewer`) — просто застосуй його і до типу тестового
харнеса, а не лише до продакшн-коду, бо харнес легко подумки виключити з
рев'ю "це ж не продакшн-код".

### Перед фіналом — перевір тест-файл на дублікати

Пройдись по всіх `it`/`test` у файлі і звір їхні асерти — якщо два тести
перевіряють ідентичний результат тим самим запитом (`getByRole`/`getByText`
тощо) без додаткової унікальної умови, лишити один, видалити дублікат. При
лінійному написанні тестів одна за одною легко не помітити, що вже написаний
раніше тест покриває те саме.

## Файлові конвенції (узгоджено з фронтенд-стандартами користувача)

- Тестовий файл співіснує поруч із цільовим файлом: `ComponentName.test.tsx`,
  `useHookName.test.ts`, `slice.test.ts`, `selectors.test.ts`.
- Тестовий файл живе поряд із тим, що він **проганяє** (компілює, рендерить,
  викликає), а не з тим, що імпортує допоміжно — критерій розміщення це
  об'єкт перевірки, не список імпортів. Тест, який компілює
  `components/X/X.module.scss`, належить у `components/X/__tests__/`, навіть
  якщо він також тягне константу з іншого шару (наприклад, `styles/`). Взірець
  форми — `Icon/__tests__/scss-sync.test.ts`.
- Будуючи `file://`-URL зі шляху файлової системи в тест-утиліті —
  `pathToFileURL(p)` з `node:url`, ніколи `new URL('file://' + p)`: друге
  пропускає percent-encoding, і парсер URL ріже шлях на `#`/`?` і декодує
  `%xx` (ламається на шляхах з такими символами, напр. CI-теки з імен гілок).
- Перед тим як оголосити локальний тест-хелпер (компіляція SCSS/JSON, обгортка
  над зовнішнім тулом, парсер фікстур) — `grep` по `src/**/*.test.*` і
  `src/tests/utils/`, чи такий хелпер уже існує. Якщо є — винеси загальну
  форму в `src/tests/utils/` і імпортуй з обох; локальну копію прибери.
- Якщо компонент організований як `Component.tsx` + `Component.types.ts` +
  `Component.module.scss` + `index.ts` — тест імпортує компонент **через `index.ts`**
  цієї ж папки (`import { UserCard } from './UserCard'`), а не напряму з `Component.tsx`,
  щоб перевіряти публічний контракт, а не внутрішню структуру файлів.
- Кінці рядків — LF (macOS), без BOM, без trailing whitespace.
- Жодного `any` у фікстурах, мок-даних чи типах пропсів — типізуй усе явно через
  інтерфейси/типи, що імпортуються з `*.types.ts` цільового модуля, або локально
  оголошені `Mock<...>`-типи для тестового файлу.

## Мок-стратегія (детально — `references/mocks-and-setup.md`)

- **Redux у connected-компонентах**: НЕ мокати селектори. Обгортати компонент у
  `renderWithProviders` з реальним стором RTK, попередньо наповненим типізованим
  `preloadedState: Partial<RootState>`. Slice-редюсери та селектори тестуються окремо,
  чистими юніт-тестами, без рендеру UI.
- **Next.js**: мокати `next/navigation` (`useRouter`, `usePathname`, `useSearchParams`)
  на рівні файлу через `jest.mock(...)`, типізовано.
- **Мережа**: моки на рівні модуля (`jest.fn()`) для простих кейсів, або MSW-хендлери
  для сценаріїв з кількома запитами / перевіркою заголовків-запиту.
- **Cleanup**: `afterEach(() => { jest.clearAllMocks(); })` — **лише якщо файл дійсно
  містить** `jest.mock`/`jest.spyOn`/`jest.fn`, які накопичують стан між тестами. Якщо
  таких викликів у файлі немає — хук не додавати: no-op `afterEach` без жодного мока
  для очищення — таке ж сміття в тесті, як і зайвий коментар, навіть якщо він
  формально нешкідливий. Стосується як генерації нового файлу, так і рев'ю/доповнення
  вже існуючого.
- **Перед тим, як заявити "цю поведінку неможливо перевірити"** через відсутність
  глобального мока для модуля — перевір (`git log --all`, `grep`), чи не існує вже
  файл-локального `jest.mock`-патерну для того самого модуля в іншій гілці чи іншому
  файлі проєкту. Мок-стратегія проєкту не обмежується лише `jest.setup.ts` —
  по-файлові моки теж усталена конвенція тут, і саме вона могла вже розв'язати цю
  задачу раніше.
- **Частковий мок браузерного API — делегуй реальній реалізації для решти.** Якщо
  потрібно підмінити лише одне значення, яке повертає `getComputedStyle`/подібний
  глобальний API (одну CSS-властивість, один метод), захопи реальну реалізацію
  **до** `jest.spyOn` і викликай її для всього, крім підміненого випадку. Повна
  заглушка (повертає `''`/`undefined` для решти) мовчки "отруює" все інше в
  jsdom/RTL, що читає той самий API, і провалюється незрозуміло, тільки коли
  хтось інший у цьому ж `describe`-блоці почне ним користуватись:
  ```ts
  const realGetComputedStyle = window.getComputedStyle;
  jest.spyOn(window, 'getComputedStyle').mockImplementation((el, pseudo) => {
    const style = realGetComputedStyle(el, pseudo);
    if (el === targetElement) {
      return { ...style, getPropertyValue: (prop) => (prop === '--custom-property' ? '20px' : style.getPropertyValue(prop)) };
    }
    return style;
  });
  ```

## Redux Toolkit — окремо (детально — `references/redux-testing.md`)

- **Slice-редюсери**: тест дефолтного (initial) стану + тест кожного екшена окремо
  (включно з edge-кейсами: порожній payload, повторний виклик, скидання стану).
- **Selectors**: перевірка коректності обчислення + тест мемоізації для `createSelector`
  (повторний виклик з тим самим інпутом не викликає перерахунку — рахуємо recompute count).
- **Thunks**: мокати `dispatch` та зовнішню залежність (API-клієнт), перевіряти
  послідовність `pending → fulfilled/rejected` дій, без реального network-виклику.

## Кастомні хуки (детально — `references/hooks-testing.md`)

### Спершу — чи варто тестувати цей хук окремо

Не кожен хук заслуговує власного `renderHook`-тесту. Пріоритезуй за цінністю:

**Тестувати обов'язково** — вузькі перевикористовувані хуки з власним інваріантом:
- робота з подіями та DOM: focus trap (цикл `Tab`, повернення фокуса), keyboard navigation (стрілки, `Enter`, межі списку), click-outside, scroll lock, обчислення overflow;
- послідовності станів із правилами переходу: захоплення → переміщення → відпускання → **скасування** (`pointercancel`);
- хуки з кількома споживачами — регресія в них ламає одразу кілька місць.

**Не вимагати тесту** — хуки-обгортки з одним споживачем і широким return (`use<Component>State`, що повертає `{ state, actions, data }`):
- такий хук — це витягнуте тіло одного компонента, а не самостійна абстракція;
- `renderHook`-тест на нього перевіряє деталі реалізації і ламається при кожному рефакторингу, нічого при цьому не ловлячи;
- якщо цю логіку варто перевірити — роби це **через компонент** (`render` + `userEvent`), тестуючи поведінку, яку бачить користувач, а не форму return'у.

> Якщо для хука не вдається сформулювати, що саме зламається непомітно без тесту — тест не потрібен. Відсутність такого тесту не є знахідкою в рев'ю (див. `code-reviewer`).

Помилку типізації тестом не ловлять — її ловить `tsc --noEmit` у CI миттєво й безкоштовно. Не пиши тест заради того, що вже покрито typecheck'ом.

### Як писати, коли тест виправданий

- Використовувати `renderHook` з `@testing-library/react`.
- Оновлення стану всередині хука — обов'язково через `act()`, якщо це не вже
  всередині `waitFor`/`findBy*` (які самі це обгортають).
- Хуки, що читають Redux, тестуються через `renderHook` з обгорткою-провайдером
  (та ж `renderWithProviders`, але для хуків, не для UI).
- Для хуків із подіями обов'язково перевіряй **cleanup**: після `unmount()`
  слухачі зняті, таймери/`requestAnimationFrame` скасовані, спостерігачі
  відключені.

## Обов'язкове покриття (checklist перед тим, як показати тест користувачу)

Для **кожного** тестованого модуля перевір, що є тест-кейси на:

- [ ] Happy path — нормальний потік із валідними даними.
- [ ] Edge cases — порожній масив/список, відсутні опціональні пропси, дуже довгий
      текст, межові числові значення (0, негативні, дуже великі).
- [ ] Async-стани — Loading / Success / Error (якщо модуль їх має).
- [ ] Доступність неявно перевіряється самим використанням `getByRole`/`getByLabelText` —
      якщо тест не може знайти елемент через роль/лейбл, це сигнал про проблему a11y
      в самому компоненті, а не привід переходити на `testid`. Повідом про це користувачу.
- [ ] Для форм — валідація (некоректне значення → повідомлення про помилку) та
      успішний сабміт із правильними аргументами викликаного handler'а. **Також:**
      Enter у жодному полі форми не викликає передчасний сабміт, окрім кнопки чи
      полів, де це явно бажано — окремий клас регресії, не покривається загальним
      "валідація + сабміт".
- [ ] **Симетричні/дзеркальні частини компонента** (два повзунки range-слайдера, дві
      сторони toggle, ліва/права панель split-view) — якщо в них різна логіка (навіть
      лише знак/напрямок обчислення), кожна сторона отримує свій тест, а не "одна за
      всіх за аналогією". Особливо критично для функцій, де знак чи напрямок
      обчислення різний (`translateX(-100%)` vs `translateX(0)`, `min` vs `max` clamp,
      `handleMinBlur` vs `handleMaxBlur`).
- [ ] **Drift-guard/sync-тест, що звіряє TS-тип із зовнішнім джерелом істини**
      (SCSS-мапа, JSON-конфіг тощо) — якщо структура, яку він захищає, має більше
      однієї незалежної осі варіативності (наприклад: розмір **і** breakpoint —
      окремо один від одного), тест покриває **кожну** вісь окремим асертом, а не
      лише ту, для якої тест писався першим. Тест, що формально існує й проходить,
      не гарантує покриття всіх осей структури, яку він нібито захищає.
- [ ] **Drift-guard читає обидві сторони з єдиного джерела, а не з рукописного
      літерала в тілі тесту.** Якщо підмножина значень фігурує в TS-типі пропа, у
      SCSS-мапі та в самому тесті — це вже три копії, кожна з яких може розійтися
      незалежно; рукописний `const SIZE_SUBSET = ['sm', 'md']` у тесті ловить дрейф
      лише в один бік (нове значення в SCSS), а не в інший (розширення TS-типу без
      SCSS). Експортуй підмножину раз (`export const X = [...] as const satisfies
      readonly Base[]`) і зроби, щоб **усі** сторони її споживали; після написання
      guard явно перевір, що розширення масиву на один елемент валить асерт в
      обидва боки.
- [ ] **`test.each`/`it.each` включає саме той вхід, поведінку якого змінив diff.**
      Коли diff **змінює** поведінку функції для конкретного входу (не додає новий,
      а змінює наявний), цей вхід має бути явно серед параметрів тесту, навіть якщо
      поруч уже є "схожі" значення — репрезентативна вибірка не замінює кейс на
      саме те значення, заради якого робилась зміна. Звір параметри `test.each` зі
      списком входів, які зачепив diff.

### Перед показом фінального тесту — звір `describe`/`it` з тілом тесту

Назва тесту — контракт для читача (`it('applies a single size class for the string
form of size', …)`), а не просто ярлик. Перед тим, як показати тест користувачу як
фінальний, чи після будь-якого редагування вже існуючого тестового файлу — звір
кожен `describe`/`it` з тілом самого тесту: чи справді асерти й дії всередині
перевіряють те, що заявлено в описі, дослівно, а не лише "по духу". Це особливо
легко пропустити після рефакторингу тестованого коду без синхронного перегляду
формулювань — тест лишається зеленим, а опис починає брехати про поведінку, яку
він насправді перевіряє. Розбіжність (застаріла назва, або назва ширша/вужча за
реальне покриття) — завжди привід поправити опис, а не мовчки лишити як є.

Застосовуй цю перевірку (і перевірку осей drift-guard вище) **в момент
написання тесту**, проактивно, а не лише коли на це вкаже рев'ювер — зелений
sync-тест, що називає неправильну гарантію, гірший за відсутність тесту.

### Компонент є або містить `<form>`, а тест мокає дочірні компоненти

Мокати дітей для ізоляції юніта — ок для перевірки логіки самого компонента, але
якщо всередині тестованої `<form>` через моки не рендериться жоден справжній
`<input>`/`<input type="radio">` — тест фізично не може перевірити keyboard-семантику
форми (Enter не сабмітить її передчасно), бо там немає нічого, куди можна натиснути
Enter. Це структурне обмеження підходу "мокати дітей", а не помилка конкретного
тесту. Якщо компонент є або містить `<form>` і тест мокає дочірні компоненти —
обов'язково додай окремий, **не ізольований** інтеграційний тест з реальними
дочірніми компонентами (`renderWithProviders`, без моків форм-елементів), що
перевіряє keyboard-семантику форми (Enter не сабмітить передчасно, Tab-порядок,
зв'язок `label`↔`control`).

Не тестуємо надлишково: внутрішні деталі рендеру, кількість викликів `console.log`,
точні class-names, snapshot-тести за замовчуванням (тільки якщо користувач явно попросить).

## Формат виводу

Кожен тестовий файл, який ти показуєш користувачу, повинен містити:

1. Повні імпорти (React — якщо потрібен, RTL-утиліти, `userEvent`, типи, ціль тестування).
2. Мок-налаштування одразу після імпортів (jest.mock для next/navigation тощо).
3. Типізовані фікстури/мок-дані без `any`.
4. `describe`-блок(и) з `it`, що покривають чеклист вище.
5. `afterEach`/`beforeEach` з очищенням моків — **лише якщо файл дійсно мокає щось**
   (`jest.mock`/`jest.spyOn`/`jest.fn`); якщо ні — не додавати no-op хук.

Це має бути **готовий до копіювання локальний код** — без пропозицій запускати
`npm test`, деплоїти чи пушити. Користувач працює виключно в ручному режимі: покажи
код, за потреби коротко поясни, що він перевіряє, і зупинись.
